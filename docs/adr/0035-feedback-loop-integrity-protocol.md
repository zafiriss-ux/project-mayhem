# ADR-0035 — Feedback Loop Integrity Protocol

**Date:** 2026-03-06
**Status:** Accepted
**Deciders:** Architect
**Source:** Risk Review V8 — Risk: Feedback Loop Corruption
**Phase:** 7.9 Hardening
**Supplements:** ADR-0020 (persistence failure policy), ADR-0021 (governance evolvability), T5-05 (recalibration — Phase 9), `titan/science/outcome_tracker.py`

---

## Context

`OutcomeTracker` was introduced in v5.7.1 (ADR-0008) to store paired governance
decisions and post-session outcomes for future threshold calibration. The table
`governance_outcomes` records:

```
decision_id  → governance recommendation (session type, intensity, gates fired)
outcome_data → post-session feedback (RPE, HRV next morning, injury flag)
```

The intended use case is Phase 9 calibration: after sufficient outcomes accumulate
(T5-05 specifies ≥90 days), the `AutomatedPeriodizationEngine` will use the
decision→outcome pairs to tune governance thresholds toward the athlete's actual
response patterns.

### The Feedback Loop Corruption Risk

This architecture creates a structural feedback loop risk:

```
Governance decision (G₁) →
  Influences training session →
    Produces outcome (O₁) →
      Stored in governance_outcomes →
        Used to calibrate governance thresholds →
          Produces governance decision (G₂) → ...
```

**The corruption scenario:**

1. Governance repeatedly recommends "easy maintenance" (e.g., due to conservative
   TSB floor threshold — `HARD_STOP_TSB_FLOOR`).
2. Athlete complies. Post-session outcomes consistently show "good RPE, recovered HRV."
3. Calibration loop reads: "when we recommend easy maintenance, outcomes are always good."
4. Calibration concludes: "easy maintenance is always the right decision."
5. The calibrated threshold drifts toward recommending even more easy maintenance.
6. The model has learned to validate its own conservative bias — not the athlete's
   true optimal load.

This is a classic **closed-loop validation failure**: the training data for the
calibration model is generated by the decisions of the model being calibrated. There
is no independent ground truth.

**A secondary corruption mode:**

If the athlete ignores governance and does a hard workout despite a HARD_STOP, and
then the outcome is "fine," the system may learn that overrides are safe — even though
the sample is survivorship-biased (the athlete who gets injured after overriding does
not have the same "fine" outcome, but the injury may not be tagged as governance-related).

### Why This Is Tier 1

The OutcomeTracker is currently storing data that will be used for calibration in
Phase 9. If it is storing data that is already corrupted by feedback loops, the
Phase 9 calibration model will be trained on corrupted data. Corrupted calibration data
is a data integrity issue — not a future optionality issue.

---

## Decision

**Introduce feedback-loop guardrails into the OutcomeTracker data model and the
Phase 9 calibration pipeline before any calibration-driven threshold adjustment occurs.**

### Guardrail 1 — Decision Independence Flag

Every row in `governance_outcomes` must record whether the outcome was:

```sql
ALTER TABLE governance_outcomes ADD COLUMN decision_was_followed INTEGER NOT NULL DEFAULT 1;
-- 1 = athlete followed governance recommendation
-- 0 = athlete overrode governance (manual override recorded)
ALTER TABLE governance_outcomes ADD COLUMN override_outcome_exclusion INTEGER NOT NULL DEFAULT 0;
-- 1 = this row is excluded from calibration (override survivorship bias)
```

**Rule:** Override outcomes (`decision_was_followed = 0`) must be excluded from
calibration training data by default. They represent survivorship-biased samples and
cannot be treated as evidence that the governance decision was wrong.

### Guardrail 2 — Outcome Independence Window

Outcomes must be recorded with a minimum independence window to break the direct
feedback path:

```python
OUTCOME_INDEPENDENCE_WINDOW_DAYS = 2   # stored in thresholds.py
```

An outcome collected within 2 days of a governance decision that directly caused the
session is subject to confounding from the same physiological state that produced the
decision. The 2-day window ensures the outcome measurement (HRV next morning) reflects
the training response, not the pre-session state that was already known.

**Implementation:** `OutcomeTracker.record_outcome()` must reject outcome records where
`outcome_timestamp - decision_timestamp < OUTCOME_INDEPENDENCE_WINDOW_DAYS * 86400`.

### Guardrail 3 — Calibration Diversity Check (Phase 9 gate)

Before any Phase 9 calibration run may proceed, the calibration dataset must pass:

```
Calibration diversity check (binary gate):
  - ≥20% of outcome rows reflect high-intensity decisions (Zone 4/5 or VO₂)
  - ≥20% of outcome rows reflect easy/recovery decisions
  - ≥10% of outcome rows reflect governance HARD_STOP events
```

**Rationale:** A dataset where 90% of outcomes follow easy-maintenance recommendations
does not provide sufficient contrast to calibrate intensity thresholds. The calibration
will amplify the conservative bias. If the diversity gate fails, a structured warning
`calibration_diversity_insufficient` must be emitted and calibration must be deferred.

### Guardrail 4 — Calibration Audit Trail

Every threshold change produced by calibration must be:

1. Logged in `governance_outcomes` with a `calibration_event_id`.
2. Accompanied by a minimum 10-outcome evidence set (cannot calibrate on fewer).
3. Bounded: no single calibration event may change any threshold by more than 10%
   of its current value (circuit breaker against runaway drift).
4. Reversible: the `governance_outcomes` table retains the pre-calibration threshold
   value and the calibration event timestamp.

```python
CALIBRATION_MAX_THRESHOLD_DELTA_PCT = 0.10   # stored in thresholds.py
CALIBRATION_MIN_OUTCOME_COUNT       = 10     # minimum evidence set
```

### What This Does NOT Change

- `OutcomeTracker` currently only stores data — no calibration logic is implemented.
  Phase 9 implements the calibration. This ADR defines the integrity contracts the
  Phase 9 implementation must satisfy.
- The existing `governance_outcomes` schema is extended, not replaced.
- The debt item T5-05 (recalibration mechanism) is updated to reference these
  guardrails as pre-conditions.

---

## Debt Items Created

- **T1-22** — OutcomeTracker schema lacks feedback-loop guardrails — calibration
  training data is not protected against circular validation and survivorship bias
  (Tier 1, data integrity; implementation prerequisite for T5-05 calibration)

---

## Alternatives Considered

**Alternative A — Use a holdout dataset for calibration validation**
A holdout set requires sufficient volume to be statistically meaningful (typically
20–30% of the training set). At the current data collection rate (~1 outcome/day), a
holdout of sufficient size would delay calibration by 120+ days beyond the T5-05
minimum. Guardrails are a more pragmatic control for this data volume.

**Alternative B — Disallow override outcomes entirely**
Rejected. Override outcomes are valuable data — they tell the system about cases where
the governance was wrong. The correct approach is to track them separately and apply
them with appropriate caution, not discard them. A future Phase 9 item may use override
outcomes as "governance error signals" with a separate analysis path.

**Alternative C — Defer all guardrails to Phase 9 when calibration is implemented**
Rejected. The schema is being populated now. Adding guardrail columns after months of
data have accumulated requires retroactive classification of rows as "override" or "not
override" — which is not feasible without historical operator logs. The schema must
capture this data from the point where override workflows are active (ADR-0012).

---

## Consequences

- Positive: Phase 9 calibration will operate on clean, bias-controlled training data.
  The risk of the system amplifying its own conservative bias through circular validation
  is structurally prevented.
- Positive: Override outcomes are preserved for separate analysis without contaminating
  the calibration dataset.
- Positive: The calibration circuit breaker (10% maximum delta per event) prevents
  runaway threshold drift even if an edge case in the calibration algorithm produces a
  spurious recommendation.
- Negative (acceptable): Schema migration required to add two columns to
  `governance_outcomes`. Low complexity — `ALTER TABLE ADD COLUMN` with defaults.
- Constraint: T1-22 must be resolved before any Phase 9 calibration logic is
  implemented. If T1-22 is not resolved, Phase 9 calibration is blocked.
