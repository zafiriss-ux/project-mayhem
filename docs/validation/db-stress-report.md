# Δοκιμή αντοχής βάσης δεδομένων TITAN OS

Ημερομηνία εκτέλεσης: 2026-10-15. Κλάδος `test/db-stress`. Κώδικας που μετρήθηκε: `main` στο commit
`0852e888141d9ed143818b1ec3eb7d8bfe194e80` (το εργαλείο δοκιμής προστέθηκε από πάνω, χωρίς καμία αλλαγή
σε κώδικα παραγωγής, σχήμα, migrations, πολιτικές διατήρησης ή ρυθμίσεις backend).

Κανόνας του εγγράφου: πρώτα μετράμε και καταγράφουμε, μετά προτείνουμε. Κάθε αριθμός παρακάτω βγήκε από
εκτέλεση που έγινε πραγματικά. Ό,τι είναι συμπέρασμα και όχι μέτρηση σημειώνεται **(συμπέρασμα)**.
Καμία αλλαγή αρχιτεκτονικής δεν εγκρίνεται επειδή φάνηκε ένα σημείο συμφόρησης.

Αρχεία:

- εργαλείο: `scripts/stress/` (`run_stress.py`, `dataset.py`, `sqlite_phases.py`, `pg_phases.py`,
  `stress_common.py`, `summarize.py`), κατώφλια `scripts/stress/thresholds.json`;
- μικρά αποτελέσματα: `scripts/stress/results/full_summary.json` (κύρια εκτέλεση, 10.000 αθλητές) και
  `scripts/stress/results/a2000_summary.json` (συμπληρωματική εκτέλεση 2.000 αθλητών, βλ. §2.4);
- δοκιμή καπνού: `tests/stress/test_stress_smoke.py` (`slow`, τρέχει το εργαλείο σε 8 αθλητές).

## 1. Περιβάλλον, backend και ρυθμίσεις

### 1.1 Μηχάνημα

| στοιχείο | τιμή |
|---|---|
| OS | Linux 6.18.44 x86_64, glibc 2.39 (container) |
| CPU / RAM | 4 πυρήνες / 15,7 GB, χωρίς swap |
| Python | 3.13.16 |
| βιβλιοθήκη SQLite | 3.45.1 |
| PostgreSQL (μόνο σύγκριση) | 16.15, προσωρινό cluster σε φάκελο μιας χρήσης, θύρα 55432 μόνο σε 127.0.0.1, σταμάτησε και διαγράφηκε στο τέλος (`cluster_destroyed: true`) |
| psutil / psycopg | 7.2.2 / 3.3.6 (ήταν ήδη εγκατεστημένα) |

### 1.2 Ποιο backend τρέχει πραγματικά

- Το μόνο backend που λειτουργεί είναι το **SQLite** μέσω `titan.core.database.DatabaseManager`.
- `get_database_manager(backend="postgres")` σηκώνει `NotImplementedError` ("disabled until ADR-0044
  full parity", T5-08). Ο `PostgreSQLDatabaseManager` (psycopg2) και ο `PostgreSQLAdapter` στο
  `titan/core/persistence.py` υπάρχουν αλλά δεν συνδέονται στην παραγωγή. Οι μέθοδοι
  `is_db_reachable` και `replay_tsb` του `PostgreSQLAdapter` σηκώνουν ακόμη `NotImplementedError`.
- Υπάρχει δέντρο Alembic (`alembic/versions/`, 10 αρχεία, μαζί με RLS policy `titan_athlete_isolation`
  και `consent_log`), αλλά το `alembic/README_FREEZE.md` λέει ότι δεν είναι συνδεδεμένο και ότι η βάση
  είναι SCHEMA_VERSION 17. Ο κώδικας είναι στο **28**. Το Alembic υστερεί κατά 11 εκδόσεις σχήματος.
  Δεν το έτρεξα.
- Άρα **το TITAN δεν έχει πραγματικό backend PostgreSQL**. Η σύγκριση στο §5 χρησιμοποιεί σχήμα που
  μετέφρασα με το χέρι και **δεν είναι το backend του TITAN**.

### 1.3 PRAGMA όπως τα ορίζει ο `DatabaseManager` (διαβάστηκαν από νέα βάση)

| PRAGMA | τιμή |
|---|---|
| journal_mode | wal |
| synchronous | 1 (NORMAL) |
| busy_timeout | 5000 ms |
| foreign_keys | 1 |
| user_version | 28 |
| page_size | 4096 |
| cache_size | -2000 (≈2 MB, προεπιλογή) |
| temp_store / mmap_size | 0 / 0 (προεπιλογές) |
| wal_autocheckpoint | 1000 σελίδες |
| locking_mode | normal |

Η σύνδεση ανοίγει με `check_same_thread=False`. Όλες οι αναγνώσεις και εγγραφές του αποθετηρίου
περνούν από ένα `threading.RLock` (`DatabaseManager._lock`). Σε κάθε άνοιγμα τρέχει
`PRAGMA foreign_key_check` (INV-14), που ελέγχει **όλο** τον πίνακα (βλ. §4.3).

### 1.4 Σχήμα, ευρετήρια, περιορισμοί (μετρήθηκαν σε νέα βάση v28)

- 25 πίνακες, 18 ευρετήρια. Βασικοί πίνακες για τη δοκιμή:
  - `training_log`: PK `id`, `athlete_id NOT NULL DEFAULT 'owner'`, `date NOT NULL`, FK μόνο
    `shoe_id → gear_usage.id`. **Μόνο ένα ευρετήριο:** `idx_training_log_garmin_id` UNIQUE στο
    `garmin_activity_id` (WHERE NOT NULL), **καθολικό για όλους τους αθλητές**. **Κανένα ευρετήριο σε
    `athlete_id` ή `(athlete_id, date)`.**
  - `daily_metrics`: `UNIQUE (athlete_id, date)` (αυτόματο ευρετήριο, καλύπτει τα ερωτήματα ανά αθλητή).
  - `athletes`: PK `athlete_id`.
- **Δεν υπάρχει FK** από `training_log.athlete_id` / `daily_metrics.athlete_id` προς `athletes`.
- **Δεν υπάρχουν CHECK constraints** (αρνητική απόσταση/διάρκεια, ΚΣ, φορτίο γίνονται δεκτά από το σχήμα).
- `training_log.quality_flag` δηλώνεται INTEGER αλλά ο κώδικας γράφει το κείμενο `'degraded'`
  (το SQLite το δέχεται λόγω type affinity, ένα PostgreSQL όχι).

### 1.5 Τι διάβασα για την προετοιμασία

ADR-0015, 0023, 0026, 0033, 0040, 0044, 0046, 0051, `docs/SLO.md`, `docs/ARCHITECTURE.md`,
`titan/core/{schema,database,persistence}.py`, `titan/core/repositories/*`,
`titan/science/data_sanity.py` (`DataSanityChecker`), `titan/orchestration/garmin_persistence.py`.
Δεν ενεργοποίησα καμία λειτουργία πολλών αθλητών στην παραγωγή. Τα πολλά `athlete_id` υπάρχουν μόνο
στις βάσεις μιας χρήσης της δοκιμής.

## 2. Σύνολο δεδομένων και αναπαραγωγή

### 2.1 Εντολή αναπαραγωγής

```bash
python scripts/stress/run_stress.py --seed 20261010 --athletes 10000 --out .stress_tmp/full
python scripts/stress/summarize.py .stress_tmp/full/results.json \
    --json scripts/stress/results/full_summary.json --md .stress_tmp/full/summary.md
```

Διάρκεια: 1.656,7 s (≈28 λεπτά). Η βάση SQLite και το cluster PostgreSQL διαγράφονται στο τέλος.
Οι ημερομηνίες των δεδομένων καταλήγουν στο `--anchor 2026-10-10`. Τα ερωτήματα του αποθετηρίου όμως
μετρούν το παράθυρο από το ρολόι του συστήματος (`date('now', '-210 days')`), γι' αυτό τα αποτελέσματα
εξαρτώνται λίγο από την ημέρα εκτέλεσης. Εδώ η εκτέλεση έγινε 5 ημέρες μετά το anchor.

Γρήγορη δοκιμή: `--small` (200 αθλητές, ≈1,5 λεπτό). Δοκιμή καπνού:
`python -m pytest --no-cov -q tests/stress` (1 passed, 5 s).

Έλεγχος ότι δεν χάλασε κάτι άλλο: `python -m ruff check .` καθαρό, και
`python -m pytest --no-cov -q` → 3493 passed, 7 skipped, 3500 collected (μαζί με τη νέα δοκιμή καπνού).

### 3.3 Φορτίο στην ανάγνωση (`get_training_load_history`)

Κύρια εκτέλεση: καμία από τις 399 `load_extreme` και τις 375 `load_negative` δεν εμφανίστηκε στο
ιστορικό. Ο τότε έλεγχος όμως δεν ξεχώριζε όσες έπεφταν έξω από το 210ήμερο παράθυρο. Η συμπληρωματική
εκτέλεση 2.000 αθλητών τις ξεχωρίζει:

| κατηγορία | μέσα στο παράθυρο, αποκλείστηκε | μέσα στο παράθυρο, εμφανίστηκε | έξω από το παράθυρο (δεν ελέγχεται) |
|---|---|---|---|
| load_extreme | 41 | 0 | 34 |
| load_negative | 36 | 0 | 30 |

Η πολιτική ανάγνωσης (`training_load > 0` στο SQL, `validate_single` στην Python) δούλεψε όπως ορίζει το ADR.

### 3.4 Εύρημα: μία κακή εγγραφή χαλάει όλο τον εβδομαδιαίο συγχρονισμό

- 802 από τους 520.000 συγχρονισμούς έκαναν rollback. 392 από `TypeError` (`'>' not supported between
  'str' and 'int'`, από `wrong_type_hr`) και 410 από `ValueError: could not convert string to float`
  (από `wrong_type_distance`, μέσω `float()` στο `save_session`).
- Μαζί τους χάθηκαν **1.027 έγκυρες δραστηριότητες** και **796 έγκυρες ημερήσιες εγγραφές** (T10/T11 FAIL).
- Η συμπεριφορά είναι ντετερμινιστική και επαναλαμβάνεται. Στο re-sync τα ίδια 81 syncs (από 52.000)
  απέτυχαν ξανά. **Ένας μόνιμα κακός δίσκος δεδομένων μπλοκάρει για πάντα την εβδομάδα του** (συμπέρασμα).
- Δοκιμή rollback με 1.000 syncs (5 έγκυρες + 1 με "10,0km"): 1.000 `PersistenceFailure`, **0 γραμμές
  έμειναν** (η ατομικότητα δουλεύει), 5.000 έγκυρες εγγραφές απορρίφθηκαν μαζί.
- Το ADR-0020/SLO-04 ορίζει degraded-conservative mode για το πρωί. Δεν ορίζει τι γίνεται με τις έγκυρες
  εγγραφές της ίδιας παρτίδας. Αυτό είναι ανοιχτή απόφαση (§6).

## 4. Μετρήσεις ανά σενάριο

Οι χρόνοι είναι σε ms. Το RSS είναι της διεργασίας της δοκιμής (και των παιδιών της). Το CPU % είναι
CPU-δευτερόλεπτα / wall (100% = ένας πυρήνας). Η στήλη `cpu_sampled_*` στο JSON δεν είναι αξιόπιστη για
τις φάσεις SQLite (ο sampler ξαναφτιάχνει τα αντικείμενα psutil και δίνει 0), οπότε δεν τη χρησιμοποιώ.

### 4.1 Κύρια φόρτωση μέσω `persist_garmin_data` (μία συναλλαγή ανά εβδομαδιαίο sync)

| μέγεθος | τιμή |
|---|---|
| syncs / αποτυχημένα | 520.000 / 802 |
| latency sync p50 / p95 / p99 / max | 0,078 / 0,188 / 0,67 / 34,6 |
| syncs/s (μόνο persist) | 6.671,5 |
| γραμμές δραστηριότητας/s (μόνο persist) | 9.594,6 (με τη δημιουργία δεδομένων: 4.349,8) |
| συνολικός χρόνος | 171,9 s (persist ≈78 s, δημιουργία δεδομένων 9,2 s, το υπόλοιπο είναι οι μετρήσεις των βημάτων ανάπτυξης και η εγγραφή αθλητών **(συμπέρασμα)**) |
| RSS max / mean | 84,1 / 75,7 MB |
| CPU | 83% ενός πυρήνα |

Το σχήμα είναι μεταφρασμένο με το χέρι: `athletes`, `training_log`, `daily_metrics` με τις ίδιες στήλες

### 5.2 NoSQL

Δεν το δοκίμασα. Οι μετρήσεις δεν δείχνουν πρόβλημα που λύνει ένα document ή KV store. Με το σωστό
ευρετήριο, όλα τα ερωτήματα ανά αθλητή είναι κάτω από 2 ms p99 στο SQLite. Οι εγγραφές φτάνουν 6.000–9.500
syncs/s. Ο φόρτος είναι σχεσιακός και χρειάζεται συναλλαγές (ένα sync = δραστηριότητες + ημερήσια
εγγραφή μαζί, idempotency με μοναδικό κλειδί). Ένα NoSQL θα έφερνε κόστος μετάβασης χωρίς μετρημένο
όφελος.

### 5.3 Υβριδικό

Δεν δικαιολογείται από τα δεδομένα. Ένα υβριδικό σχήμα (π.χ. SQLite ανά αθλητή + κεντρικό PostgreSQL
για τον coach) θα πρόσθετε συγχρονισμό, συνέπεια ανάμεσα σε δύο αποθήκες, διπλά backup και διπλές
migrations. Καμία μέτρηση δεν δείχνει ανάγκη γι' αυτό.

### 5.4 Πρόταση και αιτιολόγηση

Η απόφαση δεν βγαίνει μόνο από τον όγκο. Τι λένε οι μετρήσεις:

1. **Για τη σημερινή λειτουργία (ένας αθλητής, ADR-0015) το SQLite αρκεί με μεγάλο περιθώριο.** Ακόμη και
   με 10.000 αθλητές σε ένα αρχείο: εγγραφές < 1 ms p99, 0 κλειδώματα, ακεραιότητα και crash-safety
   σωστά, 193 MB. Τα αργά σημεία είναι ένα ευρετήριο που λείπει, ο έλεγχος FK στο άνοιγμα και το RLock.
   Όλα διορθώνονται μέσα στο SQLite.
2. **Το ADR-0044 έχει ήδη αποφασίσει PostgreSQL για τη Phase 8** (πολλοί αθλητές). Οι μετρήσεις δεν το
   αναιρούν και δεν το επιβάλλουν για λόγους ταχύτητας. Τα πλεονεκτήματα του PostgreSQL που μετρήθηκαν
   είναι λειτουργικά: RLS που απέρριψε εγγραφή σε ξένο αθλητή, πολλοί εγγραφείς χωρίς ένα κοινό lock
   αρχείου, pool. Δεν είναι η ταχύτητα: ανά συναλλαγή είναι πιο αργό από το SQLite NORMAL.
3. **Πρόταση:** μένουμε στο SQLite και διορθώνουμε τα μετρημένα σημεία (§7, Π1–Π4). Η μετάβαση σε
   PostgreSQL ακολουθεί το gate του ADR-0044 μόνο όταν ο ιδιοκτήτης αποφασίσει Phase 8, αφού κλείσουν οι
   ανοιχτές αποφάσεις του §6. **Αυτή η αναφορά δεν εγκρίνει καμία αλλαγή αρχιτεκτονικής.**

| έλεγχος εισόδου | ADR-0023 (clamp/NULL), ADR-0026 Πίνακας 1 | οι κανόνες του πίνακα εφαρμόζονται. Το Layer 3 (NOT NULL στο `date`) δεν πιάνει την ελλείπουσα ημερομηνία, γιατί ο κώδικας βάζει την ημέρα του sync |
| ελλείποντα δεδομένα | ADR-0051 | ισχύει: NULL χωρίς υποκατάστατο |
| αποτυχία εγγραφής | ADR-0020 / SLO-04 | rollback ολόκληρου του sync, degraded mode |
| backup | T1-17, `backup_database` (30 ημερήσια) | λειτουργεί. Restore μετρήθηκε μόνο ως αντιγραφή αρχείου |

### 6.2 Τι χρειάζεται νέα απόφαση του ιδιοκτήτη

1. **Κατώφλια T01–T20.** Γράφτηκαν **πριν** από οποιαδήποτε εκτέλεση και **δεν άλλαξαν** μετά. Μόνο τα
   T08/T09 (μέρος) στηρίζονται στο SLO-04. Τα T01/T02 προέρχονται από το SLO-02 με υπόθεση ότι η βάση
   παίρνει 5% του προϋπολογισμού. Τα υπόλοιπα είναι **προτάσεις** που περιμένουν έγκριση.
2. **Μερική αποδοχή μέσα σε ένα sync**: να απορρίπτεται μόνο η κακή εγγραφή (όπως κάνει ήδη το
   `DataSanityChecker` για τους κανόνες του) ή να μένει το rollback όλης της εβδομάδας; Σήμερα το
   ADR-0026 δεν καλύπτει λάθος τύπους δεδομένων.
3. **Κανόνες που λείπουν**: αρνητική απόσταση/διάρκεια, 0 km με διάρκεια, ΚΣ δραστηριότητας 255/299,
   ελλείπουσα ημερομηνία (απόρριψη ή ημέρα sync;), άκυρη ημερομηνία που αποθηκεύεται ως κείμενο,
   διπλότυπο Garmin + χειροκίνητης καταχώρησης.
4. **Σήμανση clamp**: να γράφεται `quality_flag` όταν το ADR-0023 κάνει clamp ή NULL;
5. **Πεδίο μοναδικότητας του `garmin_activity_id`**: καθολικό ή ανά `(athlete_id, garmin_activity_id)`;
6. **Διατήρηση και αρχειοθέτηση για πολλούς αθλητές** (ADR-0015 Phase 8 gate): παράθυρο, μορφή αρχείου,
   διαδικασία restore και audit read. Δεν έχει αποφασιστεί.
7. **Restore**: δεν υπάρχει γραπτή διαδικασία με χρόνο-στόχο (RTO/RPO). Μετρήθηκαν: backup 3,4 s,
   restore 0,26 s για 272 MB.
8. **Ταυτοχρονισμός**: μοντέλο διεργασιών (API + worker) ή threads πάνω σε κοινό `DatabaseManager`; Τα
   δύο συμπεριφέρονται πολύ διαφορετικά (§4.6).
9. **Συγχρονισμός Alembic ↔ SCHEMA_VERSION 28** πριν από οποιαδήποτε δουλειά της Phase 8A.
10. **Κριτήρια αποδοχής για πολλούς αθλητές** (ADR-0044 D1–D9): δεν υπάρχουν αριθμητικά όρια απόδοσης.
